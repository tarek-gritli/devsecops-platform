# Bootstrap

How to bring this platform up from nothing, and why it's not a single `terraform apply`.

Once bootstrapped, almost everything is GitOps'd — `root` watches `/infrastructure` and `/policies`, and a Kustomize-sourced child `Application` watches `/secrets`, so kube-prometheus-stack, Keycloak, Kyverno, `demo-app`, every guardrail policy, and the encrypted admin credentials all sync themselves with zero manual `kubectl apply`. But a handful of things are *deliberately* out-of-band — mostly private-key-shaped things that were never going to be committed to git — and those need to exist before the GitOps loop has anything to work with.

## One-time, per-machine (not per-cluster)

These don't get redone when you recreate the cluster — they live on your machine or on GitHub, not in the cluster:

- **Local CA + leaf cert** (`local-certs/ca.crt`, `local-certs/local.crt`, `local-certs/local.key`) — generated once via `openssl`. `bootstrap/local-ca.crt` (the public CA cert, safe to commit) is already in git; the private keys under `local-certs/` are gitignored and need to already exist on whatever machine is running this.
- **Age keypair** (`age-key.txt`) — generated once via `age-keygen`. Also gitignored, also needs to already exist.
- **`/etc/hosts`** — `127.0.0.1 demo-app.local argocd.local keycloak.local`. A host-file edit, not something Terraform or Kubernetes can express.
- **GHCR package visibility** — `demo-app` set to public once. A GitHub setting, unrelated to the cluster.
- **Local tools** — `k3d`, `helm` (with `helm repo add argo https://argoproj.github.io/argo-helm`), `kubectl`, `cosign`, `sops`, `age` on `PATH`.

If any of these are missing on a new machine, regenerate them first — they can't be scripted away, since a private key that could be regenerated by a script wouldn't be much of a private key.

## Per-cluster (redo every time you `terraform destroy` + `apply`)

```bash
terraform -chdir=terraform apply
./bootstrap/scripts/bootstrap-fresh-cluster.sh
```

The script handles, in order:

1. **`helm install argocd`** — Argo CD has to exist before it can manage itself; this was always going to be a manual step.
2. **Three `kubectl create secret tls`** (`demo-app-tls`, `keycloak-tls`, `argocd-tls`) — built from the cert files that already exist on disk. Never GitOps'd on purpose: putting a private key in a git-tracked manifest defeats the point of it being private, even before SOPS+age existed to do it properly.
3. **`kubectl create secret generic sops-age-key`** — same reasoning, for the age private key specifically. This one's slightly circular by design: it's the key that lets Argo CD decrypt *other* secrets, so it can't itself be one of the secrets it decrypts.
4. **`kubectl apply -f bootstrap/root-app.yaml`** — the one deliberate manual apply. Everything downstream of this point is automatic.
5. **`bootstrap/scripts/set-hostaliases-ip.sh --apply`** — the one genuine gotcha. `bootstrap/argocd-values.yaml`'s `global.hostAliases` pins `keycloak.local`/`argocd.local`/`demo-app.local` to the `traefik-internal-8443-service`'s `ClusterIP`, so `argocd-server` can reach Keycloak for OIDC from *inside* the cluster. That IP is assigned fresh by Kubernetes on every new cluster — whatever's committed in git is almost certainly stale after a recreation. The script waits for that Service to exist (it's created by `root`, same as everything else), looks up its real IP, and re-runs `helm upgrade` with the correct value.

## Verifying it worked

```bash
kubectl get applications -n argocd
# expect: demo-app, keycloak, kube-prometheus-stack, kyverno, policies, root, secrets — all Synced/Healthy

curl --cacert bootstrap/local-ca.crt https://demo-app.local:8443/health
# expect: {"status":"ok"}
```
